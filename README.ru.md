# x3model — модели и сцены X3: Terran Conflict / Albion Prelude ⇄ FBX

Конвертер тел (`.bob/.pbb`, `.bod/.pbd`) и сцен (`CUT1`, текстовые `*_scene.pbd`, ролики `objects/cut`) игры в FBX и
обратно. FBX открывается в Blender, 3ds Max и Maya. Два набора UV (второй нужен материалам `xt_*`), материалы-эффекты
с их параметрами, текстуры, LOD, сцены кораблей и станций с анимацией, камеры с целью.

[English version](README.md)

- **Без потерь.** Неизменённый FBX возвращается байт в байт: все 1 634 бинарных тела игры, 855 текстовых (в их
  двоичной форме) и 949 сцен (AP 3.3). Пересохранение в Blender без правок тоже даёт исходные байты.
- **Правки — точечно.** Изменённая часть модели получает пересчитанные касательные и габариты, остальные остаются как
  были. В сцене правка ключа анимации меняет ровно этот ключ: TCB, флаги и относительные повороты сохраняются.
- **По коду движка.** Форматы и интерполяция анимации (TCB, squad, наведение камер) разобраны по `X3AP.exe`
  ([docs/scene_format.md](docs/scene_format.md), [docs/formats.md](docs/formats.md)); `--bake-anim` показывает в DCC
  движение таким, как его считает игра.

**Состояние.** Круг через FBX проверен по всей игре и через Blender 5.2. **Изменённые модели и сцены в самой игре ещё
не проверялись** — сообщения о результатах приветствуются.

## Сборка

Windows, Visual Studio 2019 или новее с нагрузкой «Разработка классических приложений на C++» (в ней CMake и Ninja).
```
build.cmd
```
Результат — `build\x3model.exe`. Внешних библиотек нет: FBX читается встроенным [ufbx](third_party/ufbx), пишется
своим писателем бинарного FBX 7.4 (`src/fbx_write.cpp`), gzip распаковывается тем же ufbx. Готовый exe собирает CI
(вкладка Actions, артефакт `x3model`).

## Команды

| команда | что делает |
|---|---|
| `x3model export <вход> <выход.fbx> [--no-textures] [--unit-mm N] [--bake-anim [fps]]` | тело или сцена → FBX. Вход из игры: текстуры (`dds/*.pck`, `tex/*.jpg`) копируются в `textures\` рядом с FBX; у сцены под каждую часть подкладывается геометрия её тела. `--bake-anim` (сцены): между ключами пишутся кадры движения, как его считает движок (по умолчанию 30 в секунду) |
| `x3model import <вход.fbx> <выход.bob\|.pbb>` | FBX → тело, или сцена (если в FBX есть узел сцены) → `CUT1`; `.pbb` пишется в gzip |
| `x3model info <вход>` | содержимое тела (секции, LOD, материалы) или сцены (части; `X3_PART=n` — ключи части) |
| `x3model pack <out.cat> [--force] <путь в каталоге>=<файл> ...` | собрать каталог мода (`addon\NN.cat/.dat`); существующий каталог заменяется только с `--force` |
| `x3model verify <папка игры>` | прочитать и записать каждое тело и сцену всех каталогов, сравнить байты |
| `x3model roundtrip-fbx <папка игры> [фильтр]` | каждое тело → FBX → тело, сравнить байты |
| `x3model roundtrip-scenes <папка игры> [фильтр] [--perturb] [--bake]` | каждая сцена → FBX → сцена, сравнить байты `CUT1`; с `--perturb` в FBX правится средний ключ каждой анимированной части (сдвиг, поворот или цель камеры) и проверяется, что изменился ровно он; с `--bake` — круг через запечённый FBX |
| `x3model derive-check <папка игры> [фильтр]` | сверить вычисляемые касательные и габариты частей с данными игры |
| `x3model anim-sample <сцена> [шаг мс]` | движение каждой части по вычислителю движка (для сверки с `tools/x3scene.py`) |

`<вход>` — файл (`.bob .pbb .bod .pbd`) или файл из каталогов игры: `"<папка игры>|<путь в каталогах>"`, например
`"C:\Games\X3 Terran Conflict|objects/ships/argon/argon_M3.pbb"` (берётся тот член, который читает игра: свободный файл
в папке игры, затем последний каталог, сначала `addon`).

## Как пользоваться

1. Выгрузить модель: `x3model export "C:\Games\X3 Terran Conflict|objects/ships/argon/argon_M3.pbb" argon_M3.fbx`.
2. Править в Blender (импорт FBX по умолчанию; при экспорте включить **Custom Properties**, путь текстур — Relative).
   Не трогать свойства `x3_*` у узлов и материалов: в них то, чего нет в FBX. Все LOD видимы и лежат друг на друге;
   не отключайте лишние через «Disable in Viewports» (значок монитора): такие объекты Blender не пересчитывает и
   выгружает с устаревшим масштабом — поэтому x3model и не помечает LOD невидимыми.
3. Собрать обратно: `x3model import argon_M3_edit.fbx argon_M3.pbb`. Импорт пишет, что пересобрано и почему.
4. Положить в мод: `x3model pack "C:\Games\X3 Terran Conflict\addon\06.cat" objects/ships/argon/argon_M3.pbb=argon_M3.pbb`
   (номер — следующий свободный: игра монтирует каталоги подряд до первого пропуска; новый каталог старше всех, и его
   `.pbb` перекрывает и `.pbb`, и `.pbd` оригинала; занятый номер `pack` не перезапишет без `--force`). Новые текстуры —
   туда же как `dds/<имя>.dds`.

Сцена (корабль = сцена из тел: `*_scene.pbd`) выгружается так же; части — узлы с позой и анимацией, геометрия их тел —
дочерние узлы `…_geo` (только для показа: при импорте игнорируются). Новая часть — пустой узел (Empty) со свойством
`x3_body` (имя тела, как в `B` сцены, например `ships\props\weapondummy`).

**Анимация в Blender.** Blender читает ключи FBX как линейные и при экспорте запекает анимацию по кадрам. Для точного
результата при экспорте поставьте **Bake Animation → Simplify = 0**: тогда пересохранение без правок даёт исходные байты,
а правка ключа меняет ровно этот ключ. Со стандартным Simplify 1.0 Blender сам искажает кривую примерно на 0,3 %, и
x3model принимает такие места неизменными с этим допуском; изредка ключ из него выходит и переписывается. Опция «All
Actions» (по умолчанию включена) не мешает: из стеков «объект|действие» берётся собственное действие объекта.

- **Ключи и движение между ними.** Обычный экспорт пишет в FBX только ключи (их удобно править), и DCC рисует между
  ними прямые. В игре между ключами TCB (Кочанек–Бартелс с ease), squad для поворотов, наведение камер на цель.
  `--bake-anim` добавляет между ключами кадры этого движения, посчитанные кодом движка, — чтобы увидеть ролик таким, как
  в игре. Такой FBX тоже возвращается байт в байт; неизменённые кадры при импорте ключами не становятся, изменённый
  кадр становится новым ключом.
- **Камеры с целью** (ключи с флагом `8`): цель выгружается узлом `<камера>_target` рядом с камерой, с ключом на каждый
  ключ цели. Двигайте его — при импорте меняются ключи цели. Поворот самой камеры задаётся целью и креном и из FBX не
  берётся; в FBX он записан таким, каким его считает движок.
- **Ключ без своей позиции или поворота** (флаги `0x10`, `0x20`) не повторяет предыдущее значение: движок
  интерполирует трек и в его момент. Так он и выгружается, и при правке соседнего ключа такой ключ остаётся без значения.

## Что сохраняется

**Пересохранение без правок.** Точки, которые FBX показывает неизменными (позиция и UV — с точностью float32, нормаль —
1 % длины), берут сохранённые значения; грани, которые Blender выбросил бы (повторяющиеся углы или те же углы, что у
другой грани), в сетку не пишутся и восстанавливаются из `x3_held_faces`.

**Правки распознаются по частям.** Изменились грани или их материалы (отпечаток `x3_topology`) — группы собираются
заново; изменилась хоть одна точка части или добавлен/удалён второй UV — касательные и габариты этой части вычисляются
(как у экспортёра Egosoft: направление u, ортогонализованное к нормали, и −v; центр — среднее вершин граней, см.
`derive-check`); неизменённые части остаются как были. Изменилось число вершин/граней, объект скопирован (тот же
`x3_part`) или общая точка разошлась между частями — LOD собирается заново целиком: точки по (вершина, нормаль, UV, UV2),
грани — по материалам. Зеркальный масштаб учитывается. Сетка вне узлов LOD добавляется в LOD 0. Новые материалы без
`x3_*` получают шаблон `standard_lighting.fx` с текстурами из каналов FBX (диффуз, нормали, блик, свечение); материалы
держат свой номер по `x3_slot`, так что переименование их не переставляет.

**Сцены**: позы частей берутся относительно ближайшей части-предка (промежуточные пустышки и масштаб корня, который
Blender ставит при пересохранении, учитываются). Ключи сливаются по одному:
- сохранённый ключ, который FBX показывает неизменным, остаётся байт в байт;
- изменённый получает новую позу в своём же виде: флаги, TCB, цвет, FOV, `extra` сохраняются, относительный поворот
  остаётся относительным;
- относительные ключи после изменённого перекодируются так, чтобы их собственная ориентация не сдвинулась;
- ключ FBX там, где сохранённого нет и соседние ключи не дают позу FBX, становится новым ключом с флагами и
  параметрами предыдущего и абсолютным поворотом;
- для FBX из Blender (кадры запечены) значение в момент ключа восстанавливается как излом между соседними кадрами.

Копия части в DCC (тот же `x3_order`) становится новой частью; части упорядочиваются так, чтобы родитель шёл раньше
детей.

## Соглашения

- Единицы: 1 единица игры = 1 мм в FBX (`--unit-mm` меняет; выбранная единица хранится в `x3_unit_mm` и учитывается
  при импорте). Позиции тела нормированы (до 65536), размер задаёт значение LOD 0; в FBX — уже в единицах игры, общих
  со сценами.
- Оси: игра левосторонняя (Direct3D), FBX — правосторонняя, Y вверх: Z отражается; углы граней пишутся (a, c, b).
- Поворот частей сцены: ключи ось-угол движка (ось хранится с минусом, углы в оборотах, накопление без `0x2000`)
  применяются к строке (как в Direct3D) — проверено по картинке сцены `dock9portsscene`.
- Время ключей — миллисекунды (сумма `dt`), в FBX — секунды.
- UV: v в FBX снизу вверх (в игре — сверху вниз).

## Ограничения

- Текстовые тела с материалами эпохи X2 (`MATERIAL:`) и 4 `extern_*_dock` с испорченной записью материала не читаются
  (их не читает и игра). Числа текстовых файлов разбираются кодом движка (`TextParseInt`/`TextParseFixed16`), и
  испорченное или недостающее число — ошибка, как у движка.
- `MATERIAL3` (глобальные материалы игры) читаются, но текстуры у них в FBX нет, а **в двоичную форму такое тело
  переводится неверно**: движок подбирает каждой грани ближайший по цвету глобальный материал во время загрузки
  (`Material::FindNearestGlobal`), а в `.bob` попадает номер записи. `import` и сборка сцен с таким встроенным телом
  предупреждают об этом.
- У тела `MAT3`/`MAT5` нельзя добавить новый материал (там только классические материалы с глобальными номерами):
  `import` откажет и попросит назначить граням существующий.
- Сохранение без Custom Properties (имена узлов x3model, но нет `x3_*`) отвергается с подсказкой.
- `BONE`/`WEIG` (кости) переносятся как данные, в FBX не превращаются в скелет (в игре нет ни одного тела с ними).
- Параметры TCB (натяжение, непрерывность, смещение, ease) в DCC не редактируются: при правке они остаются у ключа,
  новый ключ берёт их у предыдущего. Крен камеры, FOV и цвет света тоже переносятся только как данные ключей.
- Движение между ключами в DCC совпадает с игрой только в `--bake-anim`; вычислитель повторяет код движка в 16.16
  (сверен с `tools/x3scene.py` на 797 843 выборках), но с самой игрой движение между ключами не сравнивалось.
- Ограничения позиции (`CONS`/`K`: позиция берётся у другой части) в FBX не показываются.
- Вложенные сцены (часть с флагом `0x80`) и тела-пустышки `types\Dummies` не подкладываются геометрией.

## Проверки

```
tests\run_checks.cmd "C:\Games\X3 Terran Conflict"
```
Читает и пишет каждое тело и сцену установленной игры, гоняет их через FBX, правит ключи и сравнивает. Ожидаемые числа
(в самом скрипте) — для AP 3.3 из Steam. Скрипты `tests/blender_*.py` проверяют круг через Blender
(`blender -b --factory-startup -P tests/blender_resave.py -- <in.fbx> <out.fbx>`).

`tools/x3scene.py` — эталонный разбор сцен на Python (только стандартная библиотека) и вычислитель анимации, с которым
сверен C++: `python tools/x3scene.py check "<папка игры>"`, `... interp "<папка игры>"`.
